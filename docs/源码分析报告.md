## 一、项目概览

## 二、业务逻辑

### 2.1 启动与生命周期

启动链路（`main.rs:3` → `lib.rs:3470` → `lib.rs:3540`）：

1. `main()` 设置 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--no-proxy-server"`，避免本地 `tauri://` 请求被系统代理劫持。
2. `run()` 注册插件：**单实例**（`com.wumiu.petra`）、开机自启、全局快捷键、自动更新。
3. 注册约 50 个 IPC 命令（`lib.rs:3519`）。
4. `setup()` 按固定顺序初始化：日志目录 → 日志轮转 → 打印环境 → 系统托盘 → 穿透看门狗 → 漫游线程 → 拖拽线程 → 置顶恢复与看门狗 → 显式 show 窗口 → 媒体轮询线程 → 音频采集线程。

顺序有两处是**刻意耦合**的，注释写明了原因：

- `lib.rs:3550`：先 `rotate_log` 再取偏移，否则偏移指向已改名的旧文件。
- `lib.rs:3573`：先按落盘偏好校准置顶，再启动看门狗，否则看门狗会立刻把窗口推回置顶。

窗口配置（`tauri.conf.json:14`）：700×700、无边框、透明、置顶、不上任务栏、无阴影。

### 2.2 显示与缩放

核心公式在 `src/main.ts:294` 与 `Live2DController.ts:122`：

```
窗口边长 = 700 × modelScale        (modelScale ∈ [0.2, 2.0])
模型显示 = 窗口边长 × 0.9          (模型自带 5% 边距)
模型缩放 s = min(displayW×0.9/cw, displayW×0.9/ch) × baseScale
```

`fit()` 的关键设计：**位置用 `window.innerWidth/Height`，大小用 `displayW`**（`Live2DController.ts:128-133`）。两者解耦，拖动大小滑块时窗口还没 resize，模型也不会画到窗口外。

缩放过程（`setModelDisplaySize`）依次做五件事：改 `winSize` → 通知引擎 → 视图缩放 → resize PIXI renderer → IPC 改真实窗口尺寸，最后以中心为基准反推窗口左上角，保证缩放时模型中心不跳。

### 2.3 点击穿透（窗口交互的核心）

这是本项目最关键的机制，由三方协作完成：

| 角色 | 职责 | 位置 |
|---|---|---|
| 前端 | 上报"哪些矩形可以点" | `main.ts:1582` `collectInteractionRegions` |
| Rust 定时线程 | 16ms 采样光标，判断当前是否命中矩形 | `lib.rs:3205` |
| Win32 | 切换 `WS_EX_TRANSPARENT` 实现穿透 | `screen.rs:85` |

**为什么不用纯 CSS `pointer-events`**：透明窗口整窗都在接收鼠标，若让 CSS 决定，窗口仍然挡着桌面。必须由 OS 层面把整个窗口设为"鼠标穿透"，只在命中区域时临时关闭穿透。

判定逻辑（`lib.rs:420` `should_accept_input`）有四个"安全阀"，任一不满足就保持穿透：

1. 前端还没上报过区域（启动加载期）→ 穿透
2. 前端超过 `INTERACTION_STATE_STALE_AFTER` 没更新（渲染卡死）→ 穿透
3. 光标不在任何矩形内 → 穿透
4. 例外：渲染器锁定期或原生拖拽中 → 整窗可点

区域上报是**变化驱动 + 10Hz 兜底**（`main.ts:1654`）：`MutationObserver` 监听 class/style/hidden 变化立即同步，另有 100ms 定时器兜底；同步前先算指纹（`regionFingerprint`），无变化且距上次不足 1s 则跳过 IPC。

Rust 侧对区域做严格校验（`lib.rs:453`）：最多 128 个矩形，坐标绝对值 ≤ 100,000，宽高必须 > 0。

`screen.rs:85` 的写入方式值得注意：先调 Tauri API（保持其内部 flags 同步），再**同步**写 `GWL_EXSTYLE`，然后最多重试 5 次回读校验。注释解释了原因——Tauri 的 `set_ignore_cursor_events` 是异步投递到事件线程，立即回读会读到旧值。

### 2.4 拖拽

两套拖拽并存：

| 类型 | 触发 | 实现 | 频率 |
|---|---|---|---|
| 整窗拖拽 | 按住模型拖动 | `drag_start` 记录抓取偏移 → 8ms 线程 `drag_follow` 直接 `SetWindowPos` | 125Hz |
| 待机边缘滑动 | 待机时拖 | 同上，但 `locked_y` 固定 y，只水平移动 | 125Hz |

选择 8ms 高频线程而不是前端 `mousemove` 的原因写在 `lib.rs:883`：**像素级连续跟随，避免每帧 IPC 延迟**。鼠标事件走 WebView 的话，每次移动都有 JS→IPC→Rust 的往返，拖动会明显滞后。

边界夹紧（`screen.rs:273`）分两种模式：

- 自由拖拽：允许拖出屏幕左右下，但顶部留 `-60` 缓冲（`screen.rs:284`）
- 待机滑动：`locked_y` 固定 y，y 方向不夹紧，否则"一拽就出来一点"

`set_model_bounds` 用 `(0,0,0,0)` 作为"自由"的哨兵值（`lib.rs:834`），这个约定被前端用来表达"不限制"。

### 2.5 自主行为引擎

`BehaviorEngine`（`src/autonomous/BehaviorEngine.ts`）是一个状态机 + 定时轮询的混合体：

| 状态 | 触发 | 行为 |
|---|---|---|
| 漫游 | 默认 | 随机选目标点，按活动等级速度移动 |
| 待机 | 用户点"待机" | 贴屏幕右下角、固定 40% 大小、倒挂 |
| 躲避 | 鼠标快速靠近 | 反向逃离，`fleeUntil` 控制持续时间 |
| 暂停 | 拖拽/菜单/对话 | `suspend(ms)` 暂停自主决策 |

轮询节奏（`main.ts:1124`）：光标 60ms 一次，屏幕工作区 2500ms 一次。

活动等级 `low/mid/high` 影响速度与决策间隔（`BehaviorEngine.ts:53`）。兴奋度 `excitement` 由鼠标速度驱动，用于渲染表现。

### 2.6 媒体与歌词

`media.rs` 轮询 Windows SMTC（系统媒体会话），500ms 一次。核心难点是**选对会话**：

```
音乐播放器（网易云/QQ音乐/Spotify…）→ rank 3
浏览器 + 标题含音乐站名        → rank 2
未知来源（VLC 等）             → rank 1
浏览器 + 其他（B站/YouTube）    → rank 0，忽略
```

（`media.rs:49` `session_rank`）

设计取舍写在注释里：浏览器会话拿不到 URL，只能靠标签标题猜；宁可把 B 站视频当视频（不显示歌词），也不要在看剧时弹歌词。

选中会话后按"标题|歌手|播放态|秒级进度|app"拼 key，key 变化才 emit（`media.rs:203`），避免每 500ms 刷一次前端。

前端拿到 `NowPlaying` 后：若无播放器时间轴（网易云常见），回退到"起播锚点 + 本地计时"（`music/LyricClock.ts`）。

### 2.7 音频可视化

`audio.rs` 用 WASAPI **回环模式**采集系统默认输出设备，1024 采样一块，通过 `audio:pcm` 事件推给前端做 FFT。

关键实现细节：

- 多声道取**算术平均**而非 RMS（`audio.rs:149`），注释说明 RMS 会丢正负号导致 FFT 失效。
- 无论数据是否可读都必须 `ReleaseBuffer`（`audio.rs:172`），否则 WASAPI 包泄漏。
- 设备异常后退避 3 秒重试，错误只上报一次（`audio.rs:49`）。
- 位深解码覆盖 8/16/24/32-bit（`audio.rs:211`）。

## 三、原理剖析

### 3.1 架构分层

```
┌─────────────────────────────────────────────┐
│ 前端 (WebView2)                              │
│  PIXI 渲染 30fps │ DOM UI │ 事件绑定          │
└──────────────┬──────────────────────────────┘
               │ IPC (约 50 个命令 / 6 个事件)
┌──────────────┴──────────────────────────────┐
│ Rust 主进程                                  │
│  ├ 状态管理（Mutex/Atomic）                  │
│  ├ 后台线程：穿透 16ms / 拖拽 8ms / 媒体 500ms│
│  │           音频采集 / 漫游 / 置顶看门狗     │
│  └ Win32 API 封装                             │
└─────────────────────────────────────────────┘
```

**职责边界很清晰**：Rust 负责一切"OS 级"的事（窗口、音频、媒体、进程），前端负责一切"视觉"的事（渲染、布局、动效）。唯一的越界是相机/光标位置——Rust 提供原始坐标，前端负责插值与表现。

### 3.2 坐标系统（三套并存）

这是最容易出 bug 的地方，代码里做了明确隔离：

| 坐标系 | 单位 | 使用方 |
|---|---|---|
| 物理像素 | 屏幕实际像素 | Win32 API（`SetWindowPos`、`GetCursorPos`） |
| 逻辑像素 | CSS px | 前端 DOM、PIXI |
| 窗口客户端 | 物理像素，相对窗口 | 穿透命中测试 |

转换点集中在两处：

- `main.ts:1583`：`scale = scaleFactor || devicePixelRatio`
- `screen.rs:320`：`cursor_client_pos` 用 `ScreenToClient` 直接返回窗口内物理坐标

注释多次强调"物理↔逻辑只在这一处换算"（`BehaviorEngine.ts:80`）。

### 3.3 参数注入时序（Live2D）

Live2D 的参数（视线、呼吸、表情）必须在**模型自身 `coreModel.update()` 之前**写入，否则会被模型内置动作重置。实现方式是**包装 `update` 方法**（`Live2DController.ts:88-99`）：

```ts
const core = model.internalModel.coreModel;
const origUpdate = core.update.bind(core);
core.update = () => { this.applyParams(); origUpdate(); };
```

这样每帧渲染前都会先写参数，解决了"视线不跟随鼠标"的 bug（改版记录里提到过）。

### 3.4 首帧预热

`Live2DController.ts:105` 附近：模型加载后先 `model.update(0)` 预热一帧，再延迟显示。这是为了修复"启动时头部部件不显示"——大模型（6666×6666）的首帧纹理上传需要时间，直接显示会先露出身体。

### 3.5 置顶看门狗

`spawn_topmost_watcher`（`lib.rs:3110`）定期检查 `WS_EX_TOPMOST` 是否还在，丢失就补回。原因是某些全屏应用（游戏、播放器）会重排 z 序，把桌宠挤下去。

### 3.6 日志系统

`log_write`（`lib.rs:223`）双通道：`println!` + 追加写文件。文件超过 1MB 在下次启动时轮转为 `pet.log.1`（`lib.rs:260`）。

三档日志：`log_line`（INFO，落盘）、`log_verbose`（DEBUG，默认不落盘，`PETRA_VERBOSE_LOG=1` 或 debug 构建开启）、`log_warn`/`log_error`。

## 四、性能分析

### 4.1 后台线程与定时器清单

| 名称 | 频率 | 位置 | 说明 |
|---|---|---|---|
| 点击穿透采样 | **16ms (62.5Hz)** | `lib.rs:3290` | 取光标 + 命中测试 + 可能写窗口样式 |
| 拖拽跟随 | **8ms (125Hz)** | `lib.rs:886` | 仅拖拽时实际工作 |
| 漫游引擎 | 16ms 左右（前端 ticker） | `BehaviorEngine` | 与渲染同帧 |
| 光标轮询（前端） | 60ms | `main.ts:1124` | `invoke` 取光标 |
| 交互区域同步 | 100ms + 变化触发 | `main.ts:1666` | DOM 扫描 + IPC |
| 媒体会话轮询 | 500ms | `media.rs:182` | COM 调用 |
| 音频采集 | 事件驱动 | `audio.rs:130` | 参考 `GetNextPacketSize` 睡眠 2ms |
| 工作区轮询 | 2500ms | `main.ts:1125` | 显示器变化 |
| 置顶看门狗 | 1000ms | `lib.rs:3112` | 仅当 `WS_EX_TOPMOST` 丢失时才补回 |
| PIXI 渲染 | **30fps 上限** | `main.ts:255` | `ticker.maxFPS = 30` |

### 4.2 已做的性能优化（源码里明确写了理由）

1. **渲染锁 30fps**（`main.ts:253`）：注释称 CPU/GPU 占用约减半，动画用真实 `dt` 驱动，降帧不改变动作速度。
2. **`powerPreference: "default"`**（`main.ts:251`）：避免独显被桌宠持续占用。
3. **`resolution` 上限 2**（`main.ts:248`）：高分屏不做无意义超采样。
4. **区域同步指纹去重**（`main.ts:1637`）：内容没变不 IPC。
5. **10Hz 兜底而非 30Hz**（`main.ts:1663`）：注释明确写了"30Hz 的完整 DOM 扫描 + IPC 会在首次点击创建信息面板时放大卡顿"。
6. **媒体 key 变化才 emit**（`media.rs:211`）：避免 2Hz 刷前端。
7. **穿透状态与真实值一致时直接返回**（`screen.rs:93`）：不做无谓的 Win32 调用。

### 4.3 可识别的开销与风险点

**（1）穿透线程 62.5Hz 全窗轮询**

每次循环都做：`GetCursorPos` + `KeyboardState`/`DragState` 读取 + `snapshot.clone()`（**克隆整个区域 Vec**）+ 命中测试。

```rust
let (snapshot, renderer_locked) = ... state.snapshot.lock().unwrap().clone() ...
```

（`lib.rs:3219`）

区域最多 128 个，每个 4 个 i32 + String id，克隆成本不高但**每秒 62 次**。建议：改为在锁内直接判断，或用 `Arc<Vec>` 共享。

**（2）缩放拖动时的高频日志**

`fit()` 每次调用都 `l2dLog()`（`Live2DController.ts:140`），而 `l2dLog` = `invoke("debug_mark")` → Rust `log_line` → **同步写文件**。

日志实证：`pet.log` 中 00:16:17 一秒内出现 12 条 `fit2:` 记录，且文件已达 163KB。拖动大小滑块时每个像素都会触发一次 IPC + 磁盘写。

建议：`fit2` 降级为 verbose 日志，或前端做 100ms 节流。

**（3）`log_write` 无条件 `println!`**

```rust
println!("[pet-debug][{level}] {s}");   // release 也执行
```

（`lib.rs:227`）

GUI 子系统下 stdout 通常无控制台，开销小但非零；高频路径（fit、drag）叠加后可见。

**（4）`main.ts` 单文件 3,770 行**

所有 UI 逻辑堆在一个文件里，模块边界靠注释维持。这直接影响可维护性，也会让 Vite 的 tree-shaking 效果打折（虽然对运行性能无直接影响）。

**（5）每次改窗口尺寸都重建 PIXI renderer**

```ts
app.app.renderer.resize(s, s);
```

（`main.ts:305`）

拖动大小滑块时每次移动都 resize canvas，可能导致 GPU 纹理重建。日志显示拖动过程中 `canvas=` 尺寸逐帧变化，说明确实在反复重建。

建议：拖动过程只改模型 scale（不碰窗口/渲染器），松手后再一次性 resize。当前 `applyModelScale` 每调用一次就 resize 一次，若滑块是 `input` 事件驱动则相当于每像素重建。

### 4.4 内存与启动

- 启动峰值 RSS 约 31–33MB（多次 `Get-Process` 观测），对一个带 WebView2 的 Tauri 应用属正常范围。
- WebView2 子进程会额外占用（每个实例通常 60–120MB），实际总占用远高于主进程。
- 冷启动到窗口可见约 1–2 秒（日志 `17:26:22` 一次性打印完 setup 全部内容）。
- 大模型（6666×6666 纹理）首次加载有明显峰值，`fit2` 日志里 `model=6666x6666` 说明贴图尺寸很大，8192 纹理在集显上可能受限于 `MAX_TEXTURE_SIZE`。

## 五、健壮性与安全

### 5.1 输入校验

| 位置 | 校验 |
|---|---|
| `sync_interaction_regions` | 数量 ≤128、id 非空 ≤128 字符、宽高 >0、坐标 ≤100,000 |
| `set_model_bounds` | 同上量级，且 `right>left`、`bottom>top` |
| `sanitize_psd_name` | 文件名清洗，防路径穿越 |
| `validate_shell_command` | 命令白名单校验（`lib.rs:2789`） |
| `url_encode` | 天气/歌词请求的参数编码 |

### 5.2 敏感数据

API Key 存储分平台：Windows 用 **DPAPI**（`lib.rs:1148` `dpapi_protect`），macOS 用 Keychain，Linux 用 `secret-tool` 或 600 权限文件。

### 5.3 失败降级

代码里大量 `let _ = ...`（忽略返回值）是有意为之：窗口操作、日志写入、状态落盘失败都不应中断主流程。关键路径（如 `sync_interaction_regions`）才向上报错。

前端穿透有"渲染卡死保护"：超过 `INTERACTION_STATE_STALE_AFTER` 没更新区域就整窗穿透，避免透明窗口永久挡住桌面 —— 这是很实用的防呆设计。

---

## 六、结论与建议

### 6.1 总体评价

架构分层干净，平台相关代码全部隔离在 `*_linux.rs` / `*_mac.rs`，Windows 实现集中在 `screen.rs`/`audio.rs`/`media.rs`，可读性好。注释密度高且写的是"为什么"而不是"做什么"，这在同类个人项目里很少见。

主要问题集中在**高频路径上的日志与 IPC**，以及**前端单文件过大**。

### 6.2 优先处理项

| 优先级 | 问题 | 建议 |
|---|---|---|
| 高 | `fit2` 日志每帧 IPC + 落盘 | 改为 verbose 或 100ms 节流 |
| 高 | 穿透线程每 62ms 克隆区域 Vec | 锁内判断或 `Arc` 共享 |
| 中 | 缩放拖动反复 resize renderer | 拖动中只改 scale，松手 resize |
| 中 | `main.ts` 3,770 行 | 按面板/功能拆分模块 |
| 低 | `log_write` 无条件 println | release 下条件编译 |
| 低 | 漫游/光标轮询频率固定 | 窗口不可见时降频或暂停 |

### 6.3 观察到的设计亮点

1. **穿透的"安全阀"设计**：任何异常状态下都回落到"穿透"，宁可点不到宠物，也不挡住桌面。
2. **双坐标系解耦**：位置用视口、大小用 displayW，解决了"拖滑块时模型跳出窗口"的经典问题。
3. **拖拽走原生线程**：8ms 直连 `SetWindowPos`，绕开 IPC 延迟，体验接近原生拖窗口。
4. **SMTC 会话分级**：用 rank 而非"第一个播放中的会话"，解决了"看视频时弹歌词"。
5. **日志轮转顺序**：先 rotate 再取偏移，避免写进已改名的文件。
